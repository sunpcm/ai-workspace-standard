# AEWS v1.1.0

AEWS v1.1.0 adds a Secondary support tier and puts GitHub Copilot in it. It is
a backward-compatible release: no existing repository must change a file,
mapping, or read order to keep passing validation.

## Highlights

- Thin GitHub Copilot adapter at
  `adapters/copilot/.github/copilot-instructions.md`.
- Template-mode validator discovery for `.github/copilot-instructions.md`, both
  at a repository root and inside `adapters/`.
- A three-tier support policy: Primary (Codex, Claude Code), Secondary
  (GitHub Copilot), and Extension reference (Cursor, Gemini CLI).

## Evidence Boundary

Each tier states what it guarantees, so a runtime claim cannot leak across
tiers.

Primary means an actively used main driver with a maintained adapter, validator
discovery, and controlled runtime-loading evidence. Secondary means the same
maintenance commitment without a runtime-evidence claim. GitHub Copilot has
static projection and a validator pass only; its IDE surface has no headless,
read-only invocation comparable to `codex` or `claude`, so a controlled probe
would require a manual editor session.

## Scope Boundary

Only the repository-wide instructions file is projected. Path-scoped
`.github/instructions/*.instructions.md` rules stay with the adopting
repository, because activation globs are editor behavior rather than canonical
knowledge routing.

## Upgrade From v1.0.0

No action is required. A repository that uses GitHub Copilot may copy the new
adapter:

```bash
mkdir -p .github && cp <aews-repo>/adapters/copilot/.github/copilot-instructions.md \
  ./.github/copilot-instructions.md
```

The stable v1 surface is unchanged. Adding a tool and a tier required no
canonical role change, which was the v1.0 exit criterion recorded in
`docs/releases/v1.0.0-readiness.md`.

The full release audit is recorded in `docs/releases/v1.1.0-readiness.md`.
